Architecture Review #2

Previous round addressed: Contact type, date utilities, domain layer, enum constants, DataState, and MonthlyViewWrapper. This round surfaces what remains.

Candidate 1

getHourAndMinute lives inside DailyView but is used by WeeklyView

Strong
DailyView/utils/getHoursAndMinute.ts DailyViewWrapper.tsx WeeklyView/WeekDayColumn.tsx DailyView/utils/getNextRdv.ts

⚠ Problem

getHourAndMinute(time: string) parses a "HH:mm" string into [hour, minute]. It lives inside DailyView/utils/, a feature-scoped directory — yet WeeklyView/WeekDayColumn.tsx imports it from there. A weekly view module reaching into a daily view module's utils is a cross-feature seam violation. If the file moves, WeeklyView breaks. The deletion test confirms this is a domain utility, not a DailyView implementation detail.

Additionally, getNextRdv.ts in the same directory calls dayjs().hour() and dayjs().minute() at module load time, not inside the function. This is a timing bug — if the component is open past midnight, it uses stale "current time" values.

🐛 Bug: getNextRdv uses stale time

AFTER — right home

graph TD TU["utils/timeUtils.ts\n─────────────\ngetHourAndMinute()\ngetNextRdv()"] WDC[WeekDayColumn.tsx] --> TU DWW[DailyViewWrapper.tsx] --> TU GNR[getNextRdv.ts removed] -.->|merged into| TU style TU fill:#dcfce7,stroke:#16a34a

✓ Locality

Time parsing lives next to date utilities. Moving DailyView/utils/ no longer breaks WeeklyView.

✓ Leverage

Fix the getNextRdv timing bug in one place. All views calling it get the fix.

Candidate 2

DayWithRdv type defined 3× — same problem as Contact was

Strong
server/calendarDomain.ts WeeklyView/WeeklyView.tsx WeeklyView/WeekTimeGrid.tsx

⚠ Problem

type DayWithRdv = (day & { rdv: rdv[] }) | null is declared independently in three files. We just fixed the identical pattern for Contact. The canonical definition lives in calendarDomain.ts (exported), but WeeklyView.tsx and WeekTimeGrid.tsx each define their own local copy instead of importing the exported one. Silent drift: the three definitions could diverge as the schema evolves.

BEFORE — 3 copies

// calendarDomain.ts
export type DayWithRdv = day & { rdv: rdv[] };

// WeeklyView.tsx
type DayWithRdv =            // ← copy
  (DayRecord & { rdv: rdv[] }) | null;

// WeekTimeGrid.tsx
type DayWithRdv =            // ← another copy
  (DayRecord & { rdv: rdv[] }) | null;

AFTER — one seam

// models/CalendarModel.ts (new)
export type DayWithRdv =
  day & { rdv: rdv[] };

// calendarDomain.ts
import type { DayWithRdv }
  from '#/models/CalendarModel.ts';

// WeeklyView.tsx — same import
// WeekTimeGrid.tsx — same import

✓ Locality

Adding a field to DayWithRdv (e.g. a future notes on day) propagates everywhere automatically.

✓ Leverage

A CalendarModel.ts becomes the natural home for future calendar domain types (WeekBounds, MonthCell, etc.).

Candidate 3

Creating an RDV does not invalidate the weekly view cache

Strong 🐛 Bug
services/calendarService.ts utils/dateUtils.ts

⚠ Problem

useAddRdv()'s onSuccess invalidates listByDay and listByMonth but not listByWeek. A user who creates an RDV while viewing the weekly calendar will see stale data — the new appointment won't appear until a page refresh. The weekly query key requires the Monday of the week, which can be computed from the RDV date using the existing getMondayOf utility from dateUtils.

BEFORE — weekly view stays stale

onSuccess: (_, variables) => {
  const { year, month } =
    parseDateComponents(variables.date);

  // ✓ daily invalidated
  queryClient.invalidateQueries({ ... listByDay });
  // ✓ monthly invalidated
  queryClient.invalidateQueries({ ... listByMonth });
  // ✗ weekly NOT invalidated
};

AFTER — all three views refresh

onSuccess: (_, variables) => {
  const { year, month, day } =
    parseDateComponents(variables.date);
  const monday = getMondayOf(
    dayjs().year(year).month(month-1).date(day)
  );

  queryClient.invalidateQueries({ ... listByDay });
  queryClient.invalidateQueries({ ... listByMonth });
  // ✓ weekly now invalidated too
  queryClient.invalidateQueries({
    queryKey: trpc.calendar.listByWeek.queryKey({
      startDay: monday.date(),
      startMonth: monday.month() + 1,
      startYear: monday.year(),
    }),
  });
};

✓ Locality

All cache invalidation for RDV creation lives in one onSuccess callback. No view-specific logic needed.

✓ Leverage

The existing getMondayOf and parseDateComponents from dateUtils make the fix a 5-line addition.

Candidate 4

useGetWeeklyRdv takes 3 integers — daily and monthly take a single value

Worth exploring
services/calendarService.ts WeeklyView/WeeklyViewWrapper.tsx

⚠ Problem

Three similar hooks, three different calling conventions:

  • useGetDailyRdv(day: Dayjs) — one argument, natural
  • useGetMonthlyRdv(month: number, year: number) — two integers
  • useGetWeeklyRdv(startDay: number, startMonth: number, startYear: number) — three integers, callers must decompose a Dayjs and remember the +1 month offset

The wrapper has to write useGetWeeklyRdv(monday.date(), monday.month() + 1, monday.year()) — the +1 is an invisible invariant that will silently break if forgotten.

BEFORE — verbose, offset-prone

// WeeklyViewWrapper.tsx
const { data = [], isLoading } = useGetWeeklyRdv(
  monday.date(),
  monday.month() + 1,  // ← easy to forget +1
  monday.year(),
);

AFTER — consistent with daily

// calendarService.ts
export const useGetWeeklyRdv = (monday: Dayjs) => {
  const trpc = useTRPC();
  return useQuery(
    trpc.calendar.listByWeek.queryOptions({
      startDay: monday.date(),
      startMonth: monday.month() + 1,
      startYear: monday.year(),
    })
  );
};

// WeeklyViewWrapper.tsx
const { data = [], isLoading } =
  useGetWeeklyRdv(monday); // ← clean

✓ Locality

The +1 month-offset invariant lives in the service hook, not scattered at every call site.

✓ Leverage

Also simplifies Candidate 3's invalidation code, which also needs to decompose the date.

Candidate 5

Contact form layout duplicated between create and edit

Worth exploring
Layout/AddContact/AddContactModal.tsx Contacts/ContactEditForm.tsx

⚠ Problem

Both files contain the same 9-field form layout (civility + name grid, email + phone grid, birth date + location grid, address, notes). The two forms are structurally identical. Adding a new field requires editing two files. The only differences are: initialValues (edit has them, create doesn't), the submit label ("Créer" vs "Enregistrer"), and the mutation called.

BEFORE — duplicated layout

// AddContactModal.tsx (~60 lines of JSX)
<Form layout="vertical">
  civility + firstname + lastname
  email + phone_number
  birth_date + birth_location
  address · notes · buttons
</Form>

// ContactEditForm.tsx (~60 lines of JSX)
<Form layout="vertical">
  civility + firstname + lastname  ← copy
  email + phone_number             ← copy
  birth_date + birth_location      ← copy
  address · notes · buttons        ← copy
</Form>

AFTER — shared form module

// Contacts/ContactFormFields.tsx
export function ContactFormFields() {
  return (<>
    civility + firstname + lastname
    email + phone_number
    birth_date + birth_location
    address · notes
  </>);
}

// AddContactModal.tsx
<Form onFinish={onCreate}>
  <ContactFormFields />
  <Button>Créer</Button>
</Form>

// ContactEditForm.tsx
<Form initialValues={...} onFinish={onEdit}>
  <ContactFormFields />
  <Button>Enregistrer</Button>
</Form>

✓ Locality

New field (e.g. "specialty") added once, appears in both create and edit forms automatically.

✓ Leverage

Deletion test: remove either form file and the field layout re-appears in the other. The layout was earning its keep in both — extract it.

Candidate 6

DataState and all view hooks silently swallow query errors

Worth exploring
components/DataState.tsx services/calendarService.ts services/contactService.ts

⚠ Problem

All wrapper components destructure only { data, isLoading } from query hooks — isError is never used. DataState has no isError prop. If a DB query fails (network timeout, Neon cold start, auth expiry), the view shows an empty state or hangs on loading indefinitely with no user feedback. The seam is already there — DataState just needs one more branch.

BEFORE — errors silently swallowed

// DailyViewWrapper.tsx
const { data, isLoading } =     // isError ignored
  useGetDailyRdv(today);

// DataState — no error branch
if (isLoading) return <Spin />;
if (isEmpty)   return <Empty />;
return <{children}>;

AFTER — errors surfaced

// DailyViewWrapper.tsx
const { data, isLoading, isError } =
  useGetDailyRdv(today);

// DataState
if (isLoading) return <Spin />;
if (isError)   return <ErrorState msg="..." />;
if (isEmpty)   return <Empty />;
return <{children}>;

✓ Locality

Error UI defined once in DataState. All views using it get error handling for free.

✓ Leverage

Small interface addition (isError?: boolean) with outsized UX improvement — Neon cold starts are common on Cloudflare Workers free tier.

Candidate 7

RdvCard accepts raw database field names as props

Speculative
DailyView/RdvCard/RdvCard.tsx DailyView/DailyView.tsx

⚠ Problem

RdvCard accepts start_hour, end_hour, rdv_type, is_confirmed — raw Prisma column names as individual props. This creates a shallow interface that mirrors the DB schema. Passing the entire rdv object would be simpler, reduce prop-drilling, and mean a schema rename only touches RdvCard's internals, not its callers.

✓ Locality

DB column rename → update one component's destructuring, not every call site.

Speculative because

The current props interface is simple enough. Only worth doing if the rdv model grows significantly or if the schema is expected to change.
