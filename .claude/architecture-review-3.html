Candidate 1

Contact name formatting duplicated in 5 files

Strong
ContactSelectField.tsx CalendarFilterBar.tsx RdvCard.tsx RdvDetailModal.tsx ContactEditForm.tsx AddRdv.tsx (handleContactChange)

⚠ Problem

The expression ${'`'}${'{'}c.civility ? c.civility + \' \' : \'\'${'}'}${'{'}c.firstname${'}'} ${'{'}c.lastname${'}'}${'`'} is copy-pasted across at least 5 files. Deletion test: if you delete one copy, the formula reappears in the other 4. There's also a second variant without civility (${'{'}rdv.contact.firstname${'}'} ${'{'}rdv.contact.lastname${'}'}) in WeekRdvBlock and CalendarCell for compact contexts. Both are domain knowledge about how to display a contact's name — they belong in one place.

BEFORE — scattered

graph TD CS[ContactSelectField] -->|copy| F["civility + firstname + lastname"] CB[CalendarFilterBar] -->|copy| F RC[RdvCard] -->|copy| F RD[RdvDetailModal] -->|copy| F CE[ContactEditForm] -->|copy| F style F fill:#fee2e2

AFTER — single seam

// src/utils/contactUtils.ts
export const formatContactName = (
  c: { civility?: string | null;
       firstname: string;
       lastname: string },
  opts?: { short?: boolean }
): string => {
  const prefix = !opts?.short && c.civility
    ? c.civility + ' ' : '';
  return `${prefix}${c.firstname} ${c.lastname}`;
};

✓ Locality

Adding a field (e.g. title) or changing the format touches one function. All five callers update automatically.

✓ Leverage

The opts.short flag unifies the compact variant (no civility) used in block views vs the full variant in forms and detail panels.

Candidate 2

SelectedRdv interface defined in both WeeklyView and MonthlyView

Strong
WeeklyView/WeeklyView.tsx MonthlyView/MonthlyView.tsx models/CalendarModel.ts

⚠ Problem

Both views define interface SelectedRdv {"{ rdv: RdvWithContact; isoDate: string }"} locally. This was flagged in round 2 as a candidate once both views shared it — that moment has come. Deletion test: removing the local copy forces it to reappear in the other file. Both files already import from CalendarModel.ts, making it the natural home.

BEFORE — two copies

// WeeklyView.tsx
interface SelectedRdv {
  rdv: RdvWithContact;
  isoDate: string;
}

// MonthlyView.tsx
interface SelectedRdv {   // ← copy
  rdv: RdvWithContact;
  isoDate: string;
}

AFTER — one seam

// models/CalendarModel.ts
/** UI state for a selected RDV
 *  with its date context. */
export type SelectedRdv = {
  rdv: RdvWithContact;
  isoDate: string;
};

// WeeklyView.tsx + MonthlyView.tsx
import type { SelectedRdv }
  from '#/models/CalendarModel.ts';

✓ Locality

Adding a field (e.g. dayNum for the monthly overflow context) happens once and propagates to both views.

✓ Leverage

If a third view (e.g. yearly) needs the same pattern, the type is already there. Same fix that resolved Contact drift in round 1.

Candidate 3

CreateRdvFormValues and EditRdvFormValues are structurally identical

Worth exploring
Layout/AddRdv/AddRdv.tsx Layout/AddRdv/RdvEditForm.tsx

⚠ Problem

Both files define a form values interface with identical fields: contact_id?, name, day, start_time, end_time, rdv_type?, is_confirmed?, additional_infos?. The semantic difference (create vs edit) doesn't require separate types — both represent the same set of Ant Design form field values. Adding a new field (e.g. a recurrence option) requires updating both.

BEFORE — duplicated

// AddRdv.tsx
interface CreateRdvFormValues {
  contact_id?: number;
  name: string;
  day: Dayjs;
  start_time: Dayjs;
  end_time: Dayjs;
  rdv_type?: string;
  is_confirmed?: boolean;
  additional_infos?: string;
}

// RdvEditForm.tsx
interface EditRdvFormValues { // ← same
  contact_id?: number; ...
}

AFTER — shared

// models/RdvModel.ts
import type { Dayjs } from 'dayjs';

export interface RdvFormValues {
  contact_id?: number;
  name: string;
  day: Dayjs;
  start_time: Dayjs;
  end_time: Dayjs;
  rdv_type?: string;
  is_confirmed?: boolean;
  additional_infos?: string;
}

// AddRdv.tsx + RdvEditForm.tsx
import type { RdvFormValues }
  from '#/models/RdvModel.ts';

✓ Locality

New field added to the form once, both components pick it up automatically.

Worth exploring because

Speculative: the fields are identical today but could legitimately diverge (edit adds an id field context, create might add recurrence). If that happens, shared type becomes a constraint. Low risk today.
